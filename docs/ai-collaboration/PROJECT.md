# AI共同開発 PROJECT.md

ドナ（Claude Code）とジョージ（ChatGPT / Codex）が、GitHub 上で人を介さずに開発指示・レビュー・修正結果を共有するための共通方針。
**このリポジトリ（sandbox）はダミーコードのみ。** HamLab 本体への適用は、人間の承認後に別途行う。

## 上位ルール（矛盾したら上位が勝つ）
1. HamLab 本体の `CLAUDE.md`（「ドナの行動ルール（最優先）」を含む）。この sandbox にはコピーを置かない。本体側が正。
2. このファイル `PROJECT.md`
3. `AGENTS.md`（Codex のレビュー観点）

`CLAUDE.md` の次の方針は、AI 共同開発でもそのまま適用する。
- 「できたっぽい」は禁止。実装後に関連動作までセットで検証してから出す。
- わからないことは「わからない」と言い、不確かなら人間に確認する。
- 中途半端に気づいたら止まって相談する。

## 役割分担
| 担当 | 役割 | してはいけないこと |
|---|---|---|
| ドナ（Claude Code） | 実装・テスト・PR 作成・レビュー指摘への修正 | マージ、本番反映、DB変更、設定変更の確定 |
| ジョージ（Codex） | PR のレビュー（指摘のコメントのみ） | ブランチへの push、修正の自動実行 |
| 人間（ユーザー） | 最終判断・マージ・本番反映・DB変更・GitHub設定の承認、`needs-human` の解決 | — |

HamLab 本体の `CLAUDE.md` にある「ChatGPT＝設計議論、ドナ＝実装」の分担と矛盾しない。ジョージの役割に「PRレビュー」が加わるだけ。

## 作業の流れ
1. 人間またはジョージが `TASKS.md` に依頼を書く（完了条件つき）。
2. ドナが `ai/<日付>-<内容>` ブランチで実装し、`ai/integration` 宛てに PR を出す。
3. PR を開くと Codex が自動でレビューする。**push しても自動再レビューはされない**ので、`@codex review` で再依頼する。
4. ドナは指摘を修正する。**自動レビューと修正は最大3往復。** 3往復で解決しない場合は `needs-human` ラベルを付けて止め、人間が判断する。
5. 「レビュー完了」の判定は 👀 ではなく、Codex のサマリーコメントの機械可読状態（`status=completed`・`commit_sha` が現在の先端と一致・未解決の指摘なし）で行う。
6. マージは人間が行う。

## 承認ルール
次は**必ず人間の承認が必要**。承認は都度・その操作ごとで、過去の承認を別の操作に流用しない。
- PR のマージ
- 本番反映（配布）
- DB の変更（スキーマ・データ・マイグレーション）
- GitHub の設定変更（Ruleset、ワークフロー権限、Secrets、トークン、App の接続）
- 外部バックアップ前の worktree 削除・履歴の書き換え

## 判断できないことの扱い
AI が判断できない事項は**勝手に確定しない**。`DECISIONS.md` の「未決事項」に、選択肢と推奨を添えて記録し、人間の回答を待つ。

## 安全基準
- 秘密情報（トークン・パスワード・承認トークン）をリポジトリ・PR・コメントに書かない。見つけたら P0 として扱う。
- 「設定漏れのときに通ってしまう」処理（fail-open）は書かない。承認ゲートは設定が無ければ拒否する。
- 例外を握りつぶして処理を続けない。
- 既存の開発環境・未コミット変更には触れない。作業は専用ブランチ／専用 worktree で行う。
- 本番環境と DB には、承認なしに触れない。
- `.github/`・`ops/ci/` の変更は CI 自身の検査を書き換えられるため、人間が内容を読んでから承認する。

## ブランチ構成
| ブランチ | 役割 |
|---|---|
| `ai/base` | 本番と同一。PR 直マージ禁止。`ops/ai/sync.sh` だけが更新する |
| `ai/integration` | AI 成果の統合先。Ruleset で保護（sandbox のみ。下記） |
| `ai/<日付>-<内容>` | ドナの作業ブランチ |

## 保護の現実
- sandbox は公開リポジトリのため、Ruleset が無料で使える。
- **HamLab 本体は非公開の無料プランのため Ruleset が使えない**（API 403）。本体では「直 push の禁止」を GitHub では強制できず、上の承認ルールを運用で守る。
- Ruleset が実際に防ぐ操作と防がない操作は `VALIDATION.md`（ブートストラップ PR で追加予定）に実機検証つきで記録する。
